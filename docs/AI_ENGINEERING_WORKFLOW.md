# AI Engineering Workflow

## Objective

The maintainer should mostly express goals and review decisions. Agents are responsible for repository inspection, planning artifacts, implementation, tests, review preparation, and keeping specs coherent.

## Canonical workflow

### Ambiguous idea or architecture question

1. Read repository instructions and relevant specs/history.
2. Explore without editing production code.
3. Identify unknowns, hard constraints, and evidence needed.
4. If the outcome is actionable, create a bounded OpenSpec proposal.

OpenSpec semantic command: `explore → propose`.

### Feature or behavior change

1. Re-establish current branch/status/baseline.
2. Read current capability specs.
3. Create or select one OpenSpec change.
4. Review proposal + delta specs + design before implementation.
5. Apply tasks in order.
6. Run focused tests continuously.
7. Verify against artifacts and inspect the full diff.
8. Run broader checks justified by the change.
9. Sync/archive the completed change when the implementation and artifacts agree.
10. Prepare one PR into `develop` with scope, behavior, tests, risks, compatibility notes, and manual validation.

### Bug

1. Read issue/report and relevant history.
2. Reproduce or establish direct failing evidence.
3. Write the expected behavior as a spec delta when the contract is missing/changed.
4. Add a failing regression test before or with the fix where feasible.
5. Fix the root cause with the smallest coherent design.
6. Verify adjacent transitions/error paths, not only the reported happy path.
7. Complete the normal review/archive/PR flow.

### Small docs/tooling-only change

OpenSpec is not a tax. If behavior is unchanged, use a normal small PR or an OpenSpec change with `skip_specs: true` only when auditability is useful. Do not invent behavioral specs for formatting or typo fixes.

### Pull-request review

Review in this order:
1. state/data-loss risk;
2. security/input trust;
3. behavioral correctness;
4. Eclipse/OSGi compatibility;
5. threading/resource/lifecycle safety;
6. public extension/API compatibility;
7. test adequacy;
8. maintainability;
9. UX/accessibility;
10. style.

Report evidence with file/method references. Separate blockers from suggestions. Do not rewrite the PR while reviewing unless explicitly asked.

## Agent autonomy boundaries

Agents may autonomously:
- inspect the repo and history;
- create/update local planning artifacts;
- edit code in the approved scope;
- run focused tests/builds;
- refactor inside the approved contract when necessary;
- update specs/design/tasks when evidence requires it.

Agents must not silently:
- expand the product support matrix;
- introduce internal Eclipse APIs when public alternatives exist;
- change Java execution environment/baseline Eclipse version;
- publish releases/update sites;
- merge/push/tag without explicit authority;
- erase or reset unrelated user work;
- bundle unrelated audit cleanup into the current change.

## OpenSpec use

OpenSpec current versions support a quick `propose → apply → archive` path plus `explore`, `update`, and `sync`; expanded profiles add finer-grained new/continue/fast-forward/verify commands. Use the commands generated by `openspec init` for the active coding tool rather than committing duplicated tool-specific prompts by hand.

Recommended habit:
- uncertain → explore;
- known bounded change → propose;
- artifacts approved → apply;
- evidence changed → update artifacts, then continue;
- implementation complete → verify/validate;
- behavior and artifacts agree → archive.

## Context discipline

- Root `AGENTS.md` should remain durable and concise enough to load every run.
- Put detailed product requirements in OpenSpec, not AGENTS.
- Put historical evidence in audits, not AGENTS.
- Put long-lived architecture constraints in `docs/ARCHITECTURE_GUARDRAILS.md` and link/read them when relevant.
- Use nested `AGENTS.md` only when a subtree genuinely needs narrower instructions.
- Do not create multiple competing plan documents for the same change.

## Verification economy

Run the cheapest test capable of disproving the current change first. Escalate based on risk:

- parser/model → focused unit tests;
- preference mappings → adapter contract tests plus targeted runtime check;
- plugin.xml/MANIFEST/target/p2 → reactor + install smoke test;
- SWT semantics → runtime/UI checks;
- OS/native/CSS behavior → declared OS/version matrix;
- docs/specs only → OpenSpec validation and link/format sanity.

Full-suite testing is valuable at integration/release boundaries; it is not a ritual after every trivial edit.
