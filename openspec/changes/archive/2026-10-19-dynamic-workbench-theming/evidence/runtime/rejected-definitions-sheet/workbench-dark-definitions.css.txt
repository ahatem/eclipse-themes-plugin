/* REJECTED candidate, not shipped. Measured on Eclipse 4.40 (see ../README.md, "Plug-in color definitions"): the claims in the
 * header below that no preference is written and that user values win are false. Eclipse mirrors each override into the instance
 * org.eclipse.ui.workbench preferences, overwrites a user value on entry and deletes it on the next theme change. */

/*
 * Eclipse Themes workbench coordination, dark family: color definitions.
 *
 * Bound only to the two dark theme ids. Stock Eclipse Dark re-tunes these color definitions for dark surfaces
 * through stylesheets bound to its own theme id (org.eclipse.e4.ui.css.theme.e4_dark), so they never apply to
 * another theme; without them hover and content-assist popups stay light and several labels (for example Git
 * ignored resources in the Package Explorer) are drawn in the system list foreground, black on a dark surface.
 *
 * Stock Dark sets them as preference overrides, which on every theme change overwrite and later delete the
 * user's own Colors and Fonts values. These rules instead override the color definition defaults, the mechanism
 * stock Eclipse uses for its own tab colors: a value the user set in Colors and Fonts still wins, no preference is
 * written, and the defaults return when another theme becomes active. The platform reads only literal colors
 * here, so the values are the stock dark values, not derived from the selected theme. Definitions of plugins that
 * are not installed match nothing. The two Git row background colors are left out on purpose: the stock value is
 * the stock tree background and would paint visible stripes on any other background.
 */
